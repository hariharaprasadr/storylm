# Training the model, end to end

This document follows the whole pipeline that produced `checkpoints/embedded_big.pt`:
where the data comes from, how it is encoded, exactly what the training loop does, how
the GPU run is wired, and how the result is judged. Every step is reproducible.

Line numbers below are as of the commit that added this file; symbol names are the
stable reference.

---

## 0. Two repositories, two halves of the pipeline

| | This repository (`StoryLM`) | Device project (`m5stack-sticks3/tinystories`) |
|---|---|---|
| Contains | model library (`storylm/`), training loop, evaluation harness, packed data, checkpoints, web visualizer | C++ story engine, corpus generator, vocabulary dump, **validator + canonicaliser binary** (`build/storygen`) |
| Needed for | packing, training, GPU run, sampling | generating the corpus and the token table, validating and rendering stories |

The engine is the teacher: corpus, vocabulary and the pass/fail verdict all come from it —
not from an external dataset. **Anything in this document marked *(engine)* needs
`./build/storygen`**, i.e. the device project built (`make` there), with the resulting
binary available as `./build/storygen` from whichever directory the command runs in
(`build/` is git-ignored here; copying the binary across is enough).

---

## 1. What is being trained, and what "good" means

| | |
|---|---|
| Architecture | decoder-only Transformer: `layers 8 · d_model 128 · heads 8 (head_dim 16) · ffn 512`, RoPE, RMSNorm, GELU, tied embeddings |
| Vocabulary / context | 3,509 ids (v4) · ctx 384 |
| Parameters | **2,024,192** = `embedding 449,152 + 8 × 196,864 + norm 128` |
| Device footprint | 1,050 KiB INT4 weights, 768 KiB KV cache INT8 |
| Objective | causal next-token prediction, **loss masked to the story tokens** |

Sources: `configs/embedded_l8_d128.yaml` (model block), `docs/tiny_model.md` §3
"Architecture" and §11, and `storylm/model.py`'s `param_report()`, which prints exactly the
numbers above. The 752-id v1 model was `1,671,296 = 96,256 + 8 × 196,864 + 128`, 867 KiB
INT4 — that figure still applies wherever this document discusses v1.

Two decisions shape everything downstream:

1. **The token table is closed by construction** — 59 control tokens + 3,450 words (v4; 30 +
   722 in v1), no BPE to train, no byte fallback; a word outside the table is a hard error at
   packing time.
   `training/prepare_data.py` (docstring, lines 1-18); rationale in `docs/tiny_model.md`
   §2 "The token table is the safety boundary" (line 41).
2. **Evaluation is the firmware validator, not perplexity.** A model that writes
   well-formed stories that no clip library can speak has failed, however good its loss
   looks (`docs/tiny_model.md` §4; `training/train_model.py` docstring).

## 2. Stage 1 — the corpus comes from the story engine or its Python mirror

Stories are generated by the C++ engine; nothing is downloaded or hand-written:

```bash
# the current generation, built in this repository (no engine binary needed)
.venv/bin/python storylm/corpus_builder.py --variants 23 --target-vocab 3450
#   -> data/processed/train.jsonl (57,960 stories) + data/vocab.json + data/series.json
.venv/bin/python training/prepare_data.py --corpus data/processed/train.jsonl \
    --vocab data/vocab.json --out data/processed/train_v4.npz

# the v1/v2 generations came from the C++ engine; the same files are pinned here as
# data/vocab_v1.json, data/vocab_v2.json, data/processed/train_v2.jsonl
```

Sources: `storylm/corpus_builder.py` (`main()`, `--variants/--target-vocab/--out-*`) and the
device project `Makefile` for the v1/v2 generations.

Each corpus row is one complete story with the prompt that produced it
(`data/processed/train.jsonl`):

```json
{"series":"bluey","mode":"adventure","place":"backyard","theme":"help","variant":…,
 "prompt":"<CHAR=BLUEY><MODE=ADVENTURE><PLACE=BACKYARD><THEME=HELP>",
 "lines":[…23 lines…],"text":"…"}
```

The worlds, friends, places and props are data (`data/series.json`: 5 series, each with
`modes`, `friends`, `places`, `props`). Adding beats or worlds grows the corpus *and* the
vocabulary at the same time (`docs/tiny_model.md` §4, lines 155-158).

**A third generation (v3) closes the vocabulary gap.** The v2 corpus used only 1,221 of
its 3,530 words, so 65 % of the tied table received no gradient at all.
`storylm/corpus_builder.py` now derives the surplus words from `data/vocab.json`, sorts
them into word classes (WordNet sense counts, lemmatised, with heuristics as fallback) and
spends them in *detail beats* — short authored frames that are grammatical for their class
(`{name} set the {word} down carefully…`, `there was still time to {word} {prop} before
bed`). Six such beats per story, plus a blocklist that keeps aggressive or distressful
words out of a bedtime corpus. Result: **3,450 of 3,530 words (97.7 %) appear in stories**;
the remaining 80 are the deliberate exclusions (function words, degree adverbs, tone) and a
handful of bank-only words. All structural guarantees still hold (200–250 words, 13–30
lines, ≤16 words/line, closed vocabulary).

**A fourth generation (v4) trims the residue.** Rebuilding with the story-word count as the
builder's target drops the 80 words nothing uses, so the table is exactly as wide as the
corpus: **3,509 ids = 59 control + 3,450 words, 100 % of them appearing in stories**, with
every structural guarantee intact (200–250 words, 20–24 lines, ≤16 words/line).

**Four dataset generations exist.** The working tree currently holds **v4**; the shipped
checkpoints (`embedded.pt`, `embedded_big.pt`) were trained on **v1**, which is still in git
history (`git show HEAD:data/vocab.json`). Earlier generations are kept as `*_v2`/`*_v3`
copies so a run can name the set it used:

| | v1 (shipped checkpoints) | v2 | v3 | **v4 (current)** |
|---|---|---|---|---|
| ids / words | 752 · 30 control + 722 words | 3,589 · 59 control + 3,530 words | 3,589 · 59 control + 3,530 words | **3,509 · 59 control + 3,450 words** |
| prompt space | 5 series × 4 modes × 3 places × 4 themes | 5 series × 8 modes × 7 places × 9 themes = 2,520 prompts | same as v2 | same as v2 |
| corpus | 2,880 stories (8.9 MB) and 57,600 (178 MB), **git history only** | 57,960 stories, 23 variants per prompt (`train_v2.jsonl`, 200 MB) | 57,960 stories (`train_v3.npz`) | **57,960 stories** (`train_v4.npz`) |
| story tokens | 15.7 M | 16.7 M (mean 289, max 296) | 16.8 M (mean 290, max 300) | same as v3 |
| distinct lines | 4,536 | 3,132 | **52,183** (3,132 authored + detail beats) | same as v3 |
| words actually used | 722 / 722 | **1,221 / 3,530 (34.6 %)** | 3,450 / 3,530 (97.7 %) | **3,450 / 3,450 (100 %)** |
| pinned here | `vocab_v1.json`, `series_v1.json` (recovered from git `d975929`), `train.npz`/`train_big.npz` in git history | `vocab_v2.json`, `series_v2.json`, `train_v2.jsonl`, `train_v2.npz` | `vocab_v3.json`, `series_v3.json`, `train_v3.npz` | `data/vocab.json`, `data/series.json`, `train_v4.npz`, `vocab_v4.json`, `series_v4.json` |

The 200 MB corpora are **committed as five gzipped shards** under
`data/processed/corpus/` (1.4–1.7 MB each; 198 MB → 8.2 MB, 24.5x, verified to join back
byte-for-byte); `make corpus-join` rebuilds `train.jsonl` from them, and the raw file itself
is git-ignored.

**Frozen copies shipped here** (so training and evaluation run without the engine):

| File | Size | Contents |
|---|---|---|
| `data/processed/corpus/train_part0*.jsonl.gz` | 8.2 MB (z) | the 57,960-story corpus, 5 shards (~40 MB raw each) |
| `data/processed/train_v4.npz` | 3.8 MB | packed v4: `meta (3509, 384, 57960)` |
| `data/vocab_v4.json` | 35 KB | 3,509 ids (`special_count 59`, `word_count 3450`) |
| `data/series_v4.json` | 5.3 KB | 5 series, 7 places / 12 props each |

## 3. Stage 2 — the token table

```bash
make vocab     # storylm/corpus_builder.py --variants 1 --target-vocab 3450  -> data/vocab.json
```

The v1/v2 tables were emitted by the C++ engine (`./build/storygen --dump-vocab`), so the
model can only ever emit ids the device can speak and render; from v3 on the Python builder
is the source of truth (`data/vocab.json` here), with the engine's own table pinned as
`data/vocab_v1.json` for the engine-built generation.

**A checkpoint's ids only mean anything against its own table.** v2 and v3 both have 3,589
ids and different word lists, so the pairing cannot be guessed from the width alone:
`storylm/vocab.py` resolves each checkpoint through the `provenance.vocab` path recorded at
save time (`storylm/vocab.py:save_checkpoint`), falls back to a unique-width match for older
artifacts, and raises `TableMismatch` when the width matches nothing or more than one
generation. Packed datasets carry the same reference in their `vocab_file` array. Every
entry point (`cli.py story|test|audit|info`, `training/sample.py`,
`training/export_story.py`, `training/memorisation.py`, `training/train_model.py`) goes
through that resolver, and `--vocab` pins a table explicitly (with a warning when it
contradicts the checkpoint's own record).

## 4. Stage 3 — packing to the exact stream the firmware consumes

```bash
.venv/bin/python training/prepare_data.py --corpus data/processed/train.jsonl \
    --vocab data/vocab.json --out data/processed/train_v4.npz
```

`encode_story()` in `training/prepare_data.py` (line 35) builds each sequence exactly as
the firmware would read it:

* `<BOS>`, then the prompt's control tags matched exactly, then per line
  `<LINE> words… </LINE>`, then `<END>`, then `<EOS>`;
* words are looked up by the same letters-only, lowercased rule as the C++
  `normalize_word()`; an unknown word raises `KeyError` — no byte fallback;
* the loss mask is `False` over the prompt and the padding and `True` from the first story
  token to `<EOS>` (lines 57-58) — **nothing is learned from predicting the prompt**.

Output `npz` (docstring lines 12-18, written at line 85):

| Array | Type | Meaning |
|---|---|---|
| `ids` | int32 `[n, ctx]` | token ids, padded with `<PAD>` |
| `mask` | bool `[n, ctx]` | where the loss applies (story tokens only) |
| `meta` | int32 `[3]` | `vocab_count, ctx, n_stories` |
| `vocab_file` | str | the table the ids index into (`storylm/vocab.py` reads it) |

The script prints the story-length distribution (lines 91-98) — that is where the context
size comes from. Measured on the pinned data sets:

| Packed file | `meta` | stories | story tokens | story length min / median / max |
|---|---|---|---|---|
| `train_v2.npz` (2.4 MB) | `(3589, 384, 57960)` | 57,960 | 16,744,783 | 273 / 289 / 296 |
| `train_v3.npz` (3.8 MB) | `(3589, 384, 57960)` | 57,960 | 16,826,196 | 278 / 290 / 300 |
| `train_v4.npz` (3.8 MB) | `(3509, 384, 57960)` | 57,960 | 16,826,196 | 278 / 290 / 300 |

Story tokens exclude the 5 prompt tokens, so the worst full sequence in the current corpus
is `300 + 5 = 305` — the reason `ctx 384` has headroom, recorded in
`configs/embedded_l8_d128.yaml`.

## 5. Stage 4 — the training loop

```bash
.venv/bin/python training/train_model.py --steps 60 --eval-every 30   # smoke: plumbing only
make train                                                            # = 300-step smoke on train_v4.npz
make train-modal                                                      # real run, Modal T4
```

`make train` writes `checkpoints/smoke.pt` (git-ignored); smoke runs never overwrite a
shipped checkpoint.

**Real training runs on Modal** (`training/modal_train.py`, §6); the local CLI refuses more
than 500 steps on `--device cpu` unless `--allow-cpu` is passed explicitly. A CPU step is
several times slower than a T4 step, so a full run belongs on the GPU; local runs exist to
prove the plumbing.

One function does the work — `train_from_packed()` in `training/train_model.py` (line 52,
returns at line 105) — so the CPU path and the GPU path cannot drift apart (module
docstring, lines 8-10). Per step:

| Aspect | Detail | Where |
|---|---|---|
| Model | `StoryLM(Config(vocab, ctx, layers=8, d_model=128, heads=8, ffn=512))` | `train_model.py:59` |
| Determinism | `torch.manual_seed(seed)`, `np.random.seed(seed)`, `seed=0` | `train_model.py:56-57`, CLI `:118-131` |
| Split | 95 / 5 train / val, `n_val = len(ids) // 20`, one shuffle | `train_model.py:67-70` |
| Batch | random sample of `batch` packed sequences (default 16) | `train_model.py:83-84` |
| Loss | `model(x, targets=x, loss_mask=m)` — masked cross-entropy | `train_model.py:85` |
| Optimiser | AdamW, `lr 3e-4`, `weight_decay 0.1` | `train_model.py:72` |
| Schedule | `OneCycleLR(..., total_steps=steps, pct_start=warmup/steps)`, 100 warmup steps | `train_model.py:73-76` |
| Gradient clipping | `clip_grad_norm_(…, 1.0)` | `train_model.py:88` |
| Logging | every `eval_every` (100) steps: `step, train, val, lr, seconds` | `train_model.py:92-104` |

CLI defaults: `--data data/processed/train_v4.npz --vocab <the table the .npz records>
--steps 300 --batch 16 --lr 3e-4 --warmup 100 --layers 8 --d-model 128 --heads 8 --ffn 512
--eval-every 100 --eval-batch 32 --device cpu --checkpoint checkpoints/smoke`.

**The validation pass is chunked.** `--eval-batch` (default 32 rows) exists because one
forward over the whole held-out split materialises `[n_val, ctx, vocab]` logits: with
57,960 stories (2,898 held-out rows), ctx 384 and a 3,509-id vocabulary that is **14.6 GiB**
and the run is killed (observed on the v1 table: `exit 137` after ~19 minutes of swapping).
The chunked pass accumulates weighted loss sums, so the number is the same up to float32
summation order (measured: 35.755424 vs 35.755421 on a 400-row subset).

The checkpoint is a plain dict — no class pickling, so it loads on any torch
(`storylm/vocab.py:save_checkpoint`):

```python
{"config": model.cfg.__dict__, "model": model.state_dict(),
 "provenance": {"vocab": "data/vocab_v4.json", "data": "data/processed/train_v4.npz"}}
```

`provenance` is what makes the checkpoint self-describing: `storylm/vocab.py` reads it to
pair the model with its table, so a 3,589-id v2 checkpoint is never decoded with the
3,589-id v3 table.

It holds **51 tensors**: the 48 block tensors, `embed.weight`, `norm.weight`, and a second
copy of the word table as `head.weight` (the head is tied, so it is duplicated in the state
dict — summing tensors gives 2,473,344 on the v4 table, while the model reports 2,024,192).

Immediately after saving, the script does what a user would do: generate one story, render
it through the engine's canonicaliser, and hand it to the validator (`train_model.py:186-204`,
*(engine)*). A smoke run therefore ends with a verdict, not just a loss:

```
$ .venv/bin/python training/train_model.py --data data/processed/train_v4.npz --steps 30 --eval-every 30
vocab 3509 | total params 2,024,192 | INT4 1050 KiB | KV INT8 768 KiB | ctx 384
step     30  train 23.733  val 23.903  lr 7.50e-05    24.0s
saved checkpoints/smoke.pt  [v4 table: data/vocab.json]
--- sample (after the engine's canonicaliser) ---
    1 lines, exact 0, repaired 0, unmatched 1 (inventory 107)
Marched marched marched … marched.
validator: reject line_too_long line 1: line exceeds word budget (exit 2)
```

That is the expected shape of a 30-step run: the loss is still very high (23.7 here; the
device project's `docs/testing.md` §2 quotes ~36 from a fresh run, while the recorded runs
reach 5.2 by step 100 and 0.26 by step 4,000), the output is not usable, and the validator
says why — the plumbing is what is being tested ("a 60-step model produces nothing usable,
which is the point").

## 6. Stage 5 — the GPU run (Modal T4)

```bash
set -a; . .env.local; set +a                      # MODAL_TOKEN_ID / MODAL_TOKEN_SECRET

modal volume create tinystory-data
modal volume create tinystory-ckpts
modal volume put --force tinystory-data data/processed/train_v4.npz /train_v4.npz
modal volume put --force tinystory-data data/vocab_v4.json /vocab_v4.json

modal run training/modal_train.py --steps 5400 --batch 64 --name embedded_v4
modal volume get  tinystory-ckpts embedded_v4.pt checkpoints/embedded_v4.pt
```

`make train-modal` runs exactly that sequence (volumes, forced upload, run, download) with
`DATA=train_v4.npz VOCAB=vocab_v4.json NAME=embedded_v4` as defaults.

| | |
|---|---|
| Image | `modal.Image.debian_slim(python_version="3.11")` + `torch==2.5.1`, `numpy==2.1.3`, `training/` and `storylm/` mounted (`modal_train.py:28-35`) |
| App / GPU | `modal.App("tinystory-lm")`, `gpu="T4"`, 4 h timeout |
| Function defaults | `steps 5400`, `batch 64`, `lr 3e-4`, `warmup 300`, `eval_every 500`, `seed 0`, `name embedded_v4`, `data_file train_v4.npz`, `vocab_file vocab_v4.json` |
| Corpus | `/data/train_v4.npz` — 57,960 stories, `meta (3509, 384, 57960)` |
| Output | `/ckpt/<name>.pt` (a `{config, model, provenance}` dict), volume committed |

The function checks that the uploaded table matches the packed `meta` before training, and
the checkpoint it writes records `provenance.vocab` — so a mis-uploaded `vocab_v2.json`
fails loudly instead of training against the wrong ids.

`--steps 5400 --batch 64` is ~6 epochs of the 57,960-story corpus: ~22 minutes of T4 time
(tens of cents), plus a 53 s image build on the first run (`training/README.md`, "Training on
a Modal GPU"). Measured on the v2 dataset (3,589 ids): **5,400 × 64 = 345,600 sequences ≈ 6
epochs in 1,411 s**, reaching train/val 0.062 (§8) — 5.4× the sequences of the local run
(1.1 epochs), for 0.002 nats less loss.

**Design choice: the GPU only trains.** Canonicalisation and validation need the engine
binary, so they stay on the host after the checkpoint is downloaded — one implementation of
the runtime path, not two.

## 7. Stage 6 — evaluation: three numbers, not one

```bash
.venv/bin/python training/sample.py --per-world 4 --repeats 5     # 100 stories, newest checkpoint
.venv/bin/python training/sample.py --seed 42 --per-world 1       # one reproducible story
.venv/bin/python training/sample.py --checkpoint checkpoints/embedded_v3.pt \
    --vocab data/vocab_v3.json --per-world 4 --repeats 5          # a pinned generation
```

`--vocab` defaults to the table the checkpoint records, so a run against the current
checkpoint needs no arguments at all; passing it explicitly is a verification, not a
requirement.

**The engine is used when it matches the table, and `storylm/validator.py` otherwise.**
The C++ `storygen` is the authority on the device, but it is built from the device project's
tables; when the vocabulary changes, a stale binary rejects every new word as
`unapproved_word`. `run_check()` / `run_canonicalize()` therefore prefer `build/storygen`
when `storygen --dump-vocab` reports the same id count as the checkpoint's table
(`data/vocab_v1.json`, 752 ids, matches the binary shipped in the device project; the 3.5K
generations fall back to Python), and otherwise validate and canonicalise in Python: an
approved-vocabulary check, the structural rules
(`unapproved_word`, `line_too_long`, `too_few_lines`, `repeated_line`, `character_mismatch`)
and a canonicaliser that matches a draft line against the prompt's beat inventory, repairing
within three word edits. The CLI is a drop-in:

```bash
python -m storylm.validator --check --series bluey --mode bedtime --place bedroom --theme help < story.txt
python -m storylm.validator --canonicalize --series gabby --mode funny --place playroom --theme share < draft.txt
```

Measured on the v3 checkpoint with the same 100-story protocol
(`--per-world 4 --repeats 5`, i.e. 4 themes × 5 worlds × 5 repeats):

```
100/100 stories passed the firmware validator
2128/2201 lines match an engine line word for word (96.7 %)
302/2201 lines are not in this prompt's inventory (13.72 %) → the fallback tier
```

The 13.7 % is the detail-beat share (§2): lines the corpus builder invented are not in the
*engine's* inventory, so the runtime would substitute its own line for them. On v2 the same
figure was ~0.1 %. Our host inventory (~100 lines per prompt, the authored banks) is smaller
than the device engine's (the v1 docs quote 3,000–4,500 lines), so on-device more of those
lines would match or be repaired inside the 3-edit window.

`training/sample.py` runs the device's full path for every world × theme —
**generate → canonicalise → validate** — and prints three numbers (`sample.py:126-146`):

| Metric | What it catches |
|---|---|
| Validator pass rate | would the device show this story at all |
| Lines word-exact to an engine line | is the model reproducing the engine's beats |
| Lines outside the prompt's inventory | drift, or a beat written for another theme — the only lines the engine's fallback tier has to cover |

Lines are compared word-wise because the table is letters-only: punctuation must not be
counted as drift (`sample.py:42-43`). A pass rate alone cannot see
`"tucked themselves in the shelf"` — every word there is approved (device project
`docs/testing.md` §3, "One story, in the shape you would actually ask for it").

Runtime sampling rules that make the pass rate possible (in `storylm/model.py`'s
`generate_story` / `generate_story_cached`): stop on `<END>`, mask `<EOS>` so a story
cannot be truncated mid-line, generate one line at a time, and resample a line that
duplicates an earlier one (`training/README.md`).

**KV-cache parity** — the cache is the classic source of silent numerical wrongness, so it
has its own equivalence test:

```bash
.venv/bin/python cli.py test        # or: .venv/bin/python storylm/test_cache.py
#   checkpoint checkpoints/embedded_v4.pt  [v4 table: data/vocab.json, 3509 ids]
#   logits: worst max-abs diff 1.91e-05 -> ok
#   greedy stories identical with and without the cache: yes
#    no cache: 1.59s for 289 tokens (5.5 ms/token)
#    KV cache: 0.60s for 289 tokens (2.1 ms/token)
#   speedup: 2.7x
```

**Determinism**: the same checkpoint plus `--seed N` reproduces a story character for
character (device project `docs/testing.md` §3).

one of the corpus's closed 3,450. Freshness comes from authoring more beats, props,
casts and worlds — the corpus generator then scales for free (§4, lines 155-158). For a
genuinely creative model the lever is per-layer embeddings, not more layers here (§4,
lines 159-162), and fine-tuning a published TinyStories checkpoint was rejected for
output-channel reasons, not quality (§8, line 259).

## 9. Is it memorising? (the overfitting audit)

The validator cannot see overfitting: every word of a copied line is approved, so
`storygen --check` returns `ok` for a story lifted straight out of the corpus.
`training/memorisation.py` (`make audit`) asks the question directly, with four
measurements:

| # | Measurement | What copying would look like |
|---|---|---|
| 1 | **Overfitting gap** — masked CE on the training rows vs the same held-out 5 % split the training loop itself uses (same seed, same permutation) | val ≫ train |
| 2 | **Story-level copying** — the longest run of *consecutive* lines a generated story shares with a single training story, compared with the same number for corpus stories against the rest of the corpus (the engine's own baseline) | runs near a whole story (≈23 lines) |
| 3 | **Line inventory reuse** — share of generated lines present anywhere in the corpus | ≈100 % by design; listed for context |
| 4 | **Variety** — distinct stories per prompt when only the dice change | collapsing to a handful of corpus stories |

Measured on both shipped checkpoints (100 generated stories = 5 worlds × 4 themes ×
5 repeats, temperature 0.8):

| | `embedded.pt` — 2,880 stories, 0.78 M story tokens | `embedded_big.pt` — 57,600 stories, 15.7 M story tokens |
|---|---|---|
| Masked CE, training rows | 0.260 | 0.266 |
| Masked CE, held-out 5 % | 0.260 | 0.266 |
| **Gap** | **−0.000 nats** | **−0.000 nats** |
| Longest shared line-run (max / mean / p95) | 3 / 2.52 / 3 | 4 / 3.25 / 4 |
| Stories with a shared run ≥ 6 lines | 0 / 100 | 0 / 100 |
| Engine baseline, corpus vs the rest (max / mean / ≥6) | 4 / 2.33 / 0 | 7 / 5.43 / 58 |
| Generated lines present in the corpus | 2,266 / 2,283 = 99.3 % | 2,299 / 2,300 = 100.0 % |
| Distinct stories, 5 repeats per prompt | 100 / 100 | 100 / 100 |

Reading it:

* **No held-out penalty** on either checkpoint: the split the model never trained on is
  predicted exactly as well as the rows it did.
* **No story-level copying**: not one of 100 generated stories shares a six-line run with
  any training story. The small checkpoint is the harder case for memorisation — 0.78 M
  training tokens is less than half the 1.67 M parameters — and it is still flat.
* **More variety than the teacher**: on the larger corpus, generated stories share fewer
  consecutive lines with each other (max 4, mean 3.25) than the engine's own variants of the
  same prompt do (max 7, mean 5.43).
* The 99–100 % line reuse is the *design*, not a leak: the model is supposed to reproduce the
  engine's beats word for word. The discriminating question is whether it replays beat
  *sequences*, and it does not.

What this does not prove: generalisation to a prompt family that never appeared in the
corpus. Every world × mode × place × theme combination is in the corpus (12 variants per
combination in the small corpus, 240 in the large one), and holding one out would also leave
its prompt control token with no gradient — that experiment needs a retrain with the family
excluded and is not run here.

```bash
make audit                                    # newest checkpoint + its own corpus/split

# a pinned generation: the checkpoint's table comes from its provenance, the packed
# split from train_<generation>.npz, and the corpus from the matching .jsonl
.venv/bin/python training/memorisation.py --checkpoint checkpoints/embedded_v2_gpu.pt \
    --corpus data/processed/train_v2.jsonl --packed data/processed/train_v2.npz \
    --stories 225 --repeats 5                                     # ~5 min
```

The v2 audit is the interesting one to read against the *baseline* rather than against a
fixed threshold: there, independent engine stories already share a mean of 13.5 consecutive
lines, and the model tracks that (13.27) exactly — see §8.

## 11. Gotchas worth knowing before re-running any of this

* **A checkpoint is only valid against its own token table.** Ids are positions in a list,
  and v2/v3 both have 3,589 of them with different words, so nothing can be inferred from
  the width alone. `storylm/vocab.py` reads the `provenance.vocab` path stored in the
  checkpoint (and `vocab_file` in a packed `.npz`), refuses a mismatch, and refuses an
  ambiguous width for an artifact that records nothing; pass `--vocab` to pin a table
  deliberately, which warns when it contradicts the checkpoint's own record (`cli.py info`
  prints the pairing for every checkpoint).
* **Evaluation needs the C++ engine only where the tables agree.** Every
  `./build/storygen --check/--canonicalize` call *(engine)* lives in the device project, and
  `build/` is git-ignored here, so copying the built binary in is enough and adds nothing to
  the repo. **The engine must match the vocabulary**: the binary in the device project is
  built on the 752-id v1 table, so it validates v1 checkpoints (`data/vocab_v1.json`) and
  cannot judge a 3.5K model (every new word comes back `unapproved_word`). That is why the
  training and story CLIs go through `storylm/validator.py`, which uses the binary only when
  its id count matches the checkpoint's table and validates in Python otherwise.
* **Memory scales with `vocab × ctx × rows`.** Anything that runs a forward pass over many
  rows at once (validation, audits) must chunk: the logits tensor is
  `rows × ctx × vocab × 4` bytes, which is 14.6 GiB for the full 2,898-row validation split
  at the v4 table (15.6 GiB by the 10⁹-byte convention). `train_from_packed` chunks it via
  `eval_batch` (default 32); `memorisation.py` chunks at 16.
* **Every vocabulary id must actually occur in the corpus.** The tied head only receives a
  gradient for ids that appear as inputs or targets, so a word the corpus never uses stays
  at its random initialisation and can still be sampled. The v2 set was the worst case:
  1,221 of 3,530 words used (65 % of the table — 295,552 parameters, ~148 KiB of INT4
  weights — carried no signal). v3 spent the surplus in detail beats (97.7 %) and v4 trimmed
  the 80 unused words, so the current table is **3,450 / 3,450 words (100 %)**; keep that
  property when adding beats or worlds.
* **Path defaults are relative.** `prepare_data.py`, `train_model.py` and `sample.py` read
  `data/…` and write `checkpoints/…` relative to the working directory, so run them from
  the repository root.
* **Smoke runs write their own file.** `training/train_model.py` defaults to
  `--checkpoint checkpoints/smoke` (git-ignored) precisely so a 300-step plumbing run cannot
  overwrite a shipped checkpoint; pass `--checkpoint /tmp/smoke/embedded` for a scratch run.
* **The token table is closed.** A new word needs a table entry, a narration clip, and a
  re-pack — `prepare_data.py` hard-errors on anything outside the table.
* **The tied head appears twice** in the checkpoint dict (`embed.weight` and
  `head.weight`): 51 tensors, 2,473,344 raw elements versus 2,024,192 reported parameters on
  the v4 table. Count with `StoryLM.param_report()`, never by summing tensors.
* **Sample size matters.** 100 stories is ≈2,300 lines; differences below ~0.5 % are inside
  the noise at that size (device project `docs/testing.md`, "Limits, stated plainly"). A
  5-story sanity run is legitimate for checking the plumbing, not for quality claims.
* **Determinism.** Same checkpoint plus `--seed N` reproduces a story character for
  character. The web walkthrough keeps the same idea in the browser (seeded dice, seed 0).
* **The web visualizer does not need any of this.** It ships the exported fp16 weights
  (`web/story_data.js`, produced by `training/export_story.py`) and computes everything in
  the page; `make trace`, `training/export_trace.py` and `web/trace_data.js` no longer exist.
