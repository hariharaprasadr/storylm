How it started

From a cloud microphone to a 2.02M model

The project did not start as a language model. It started as the opposite — streaming audio to the cloud — until the requirements flipped the design.

01 · Cloud

Streaming audio to the cloud

The first experiments with pocket-sized ESP32-S3 boards streamed the microphone to a server, ran speech-to-text, a cloud LLM and text-to-speech there, and streamed the audio back. The pipeline worked — but without Wi-Fi, a gateway and someone else’s API, the gadget was a paperweight, and every word spoken to it left the house.

02 · The flip

The requirements flipped the design

The real goal was a bedtime device for a 6–8 year old: the child picks a character and a mode, and the device writes and narrates a 200–250 word story that always ends with everyone asleep. No cloud service, no LAN server, no runtime Internet after flashing. With the network gone, neural TTS is out too — narration is pre-recorded clips, so every word the device can ever say must be known in advance.

03 · The engine

A story engine came before the model

The first build was a deterministic C++ story engine: five character worlds, a fixed “sleep spine” plot skeleton, sixteen beat tables and a validator. It solved narration and safety — but it is dice: beats are picked from pools, and every story is assembled, never written.

04 · The teacher

The engine became the teacher

The same tables generate the training corpus and the entire vocabulary, closed by construction: today’s table is 3,509 ids = 59 control tokens + 3,450 words — and every one of those 3,450 words actually occurs in the corpus, so no embedding row is left at its random initialisation. A ~50K-parameter beat selector was on the table too, but a word-level generator is the whole point. So a 2.02M-parameter decoder-only Transformer was trained from scratch: v1 (752 ids, 2,880 stories) a few thousand steps on a laptop CPU, then the expanded corpus on a rented T4, and from v3 the Python mirror of the engine widened the table to 3,500 words and the corpus to 57,960 stories — the v4 run below is what ships. Evaluated by the firmware validator and the memorisation audit, never perplexity.

05 · StoryLM

That model is StoryLM

Somewhere along the way the interesting artifact stopped being the appliance and became the model: a complete language model — tokenizer, training loop, checkpoints, a KV cache proven token-identical to full recompute (2.7× faster), a forward-pass tracer and the 30-step walkthrough — that fits in 1050 KiB of INT4 flash.

Deep dive

Every component, and why it earned its bytes

Parameter counts, the maths, and the embedded tradeoffs behind each building block.

01 • Vocabulary

3,509 Closed Token Vocabulary

Unlike open-domain LLMs that rely on 32k–128k subword BPE tokenizers with byte fallback, this model operates on an entirely closed 3,509-token table: 59 atomic control tokens (e.g. <CHAR=BLUEY>, <LINE>, <END>) and 3,450 words extracted from the story engine.

• Total IDs: 3,509 (59 control + 3,450 words)
• Generation: v4 table (v1 was 752 ids)
• Out-of-vocabulary rate: 0.0% (closed domain)
• Unapproved word risk: physically impossible (no logits)
02 • Weights optimization

Tied Input/Output Embeddings

The token embedding tensor [3509, 128] is weight-tied with the output classification head (head.weight = embed.weight). The model uses the exact same vector representation for token intake and token probability projection.

• Weight shape: [3509, 128]
• Parameter count: 449,152 params
• Memory saved: 449.15 KB (50% of the vocab footprint)
03 • Normalization

Root Mean Square Normalization

RMSNorm replaces traditional LayerNorm. Instead of computing both mean and variance, it scales activations solely by their root mean square: RMS(x) = √(∑ xi2 / d). This eliminates mean-centering subtraction passes, speeding up inner loops on ESP32-S3 SIMD.

• Per layer: 2 RMSNorms (pre-attn & pre-ffn)
• Final norm: 1 RMSNorm [128]
• Biases: zero (no bias parameters anywhere)
04 • Attention mechanism

Fused Multi-Head Attention

Projects the 128-dimensional hidden state into Query, Key, and Value vectors in a single fused linear layer [128, 384]. 8 attention heads with dimension 16 calculate scaled dot-product causal attention: softmax(Q × KT / √16) × V.

• Heads: 8 heads × head_dim 16 = 128 width
• Per-layer params: qkv 49,152 + proj 16,384 = 65,536
• Total attention params (8 layers): 524,288 params
05 • Position encoding

Rotary Position Embeddings (RoPE)

Rather than storing learned absolute positional lookup tables (which take precious flash memory and fail to extrapolate), RoPE rotates Query and Key vector pairs in 2D coordinate planes using precomputed cosine and sine frequencies: freqs = pos × 10000−2i/d.

• Max context window: 384 tokens
• Memory footprint: zero flash weights (computed on the fly)
• Property: relative token distance strictly preserved
06 • Runtime acceleration

Preallocated Key-Value Cache (KVBuf)

Stores previous Keys and Values in a dedicated buffer ([1, 8, ctx, 16] per layer). The prompt is processed once during prefill; each new token only calculates its own single QKV projection and appends to the cache, converting an O(N2) loop into an O(1) step.

• Buffer shape: 8 layers × 2 (K/V) × 384 ctx × 16 head_dim
• Cache RAM size: 768 KiB in INT8 (9.6% of 8 MB PSRAM)
• Host speedup: 2.7× wall-clock, token-identical output
07 • Non-linearity

GELU Feed-Forward Network

A two-layer MLP expanding hidden representations from d_model=128 to ffn=512 via w_up, passing through Gaussian Error Linear Unit (GELU) activation, and projecting back to 128 via w_down with a residual addition: x = x + down(GELU(up(norm(x)))).

• Up / down projections: [128, 512] and [512, 128]
• Per-layer FFN params: 131,072 params
• Total FFN params (8 layers): 1,048,576 params
08 • Quantization

Groupwise INT4 Compression

To fit the entire 2,024,192 parameters into the target's 8 MB flash, weights are quantized to symmetric 4-bit integers (two weights per byte) with FP16 scale factors per group of 64 weights. Activations remain INT8/FP16, enabling SIMD dot products on the microcontroller.

• Effective bit-width: 4.25 bits/weight (4-bit + FP16 scale/64)
• Weight binary size: 1050 KiB
• Full model footprint: 1050 KiB weights + 768 KiB cache = 1,818 KiB

Design choice 1

The engine is the teacher

Every training sentence was generated by the same C++ engine that runs on the device, so the model can only ever learn words the device can speak. That is what makes "every word has a narration clip" a property of the model instead of a hope.

Design choice 2

Loss masked to the story

Prompt tokens and padding carry no loss, so the model is trained only to continue after <LINE> — it learns to write the story, not to re-predict the child's choices. The mask is built by the same script that encodes the tokens.

Design choice 3

The cache is tested, not assumed

The decoder ships with a KV cache because the device cannot afford a full recompute per token. A dedicated test proves the cached path matches the uncached one: worst logit difference 1.9e-5, greedy stories identical, 2.7× faster on a 289-token story.

Design choice 4

Checked for memorisation

The validator cannot see a story copied out of the corpus — every word in it is approved. So the split the model never trained on is scored separately, and every generated story is compared against the whole corpus. On the shipped checkpoint (225 stories): held-out loss equal to training loss (gap +0.001 nats), shared line-runs at the engine's own baseline (mean 11.69 against 11.78), every generated word one the corpus uses (100.0 %), and 225/225 distinct stories for repeated prompts.

Honest ceiling

It beats the dice, not the author

Trained on the engine's own templates, the model learns the template distribution: it chooses which beat comes next, and in which order, better than a random draw — but it cannot invent new sentences. Freshness comes from authoring more beats, props and worlds; the corpus generator then scales for free.

One model, four generations — and how a checkpoint finds its table

Ids are positions in a list, so a checkpoint only means anything against the table it was trained on — and v2 and v3 both have 3,589 ids with different word lists, so the pairing cannot be guessed from the width. Every checkpoint records provenance.vocab when it is saved, every packed dataset records vocab_file, and storylm/vocab.py refuses a mismatch or an ambiguous width rather than decode the wrong words. python cli.py info prints the pairing for every checkpoint in the tree; --vocab pins one deliberately (warning when it contradicts the checkpoint’s own record). The four generations are kept side by side, so any run can be reproduced against the set it used.

Pillar 1

Computational Scale

A standard 7B model requires roughly 3,500× more parameters and >5,000× more multiply-accumulate operations per token than the StoryLM. The StoryLM fits entirely into the 8 MB PSRAM of an embedded microcontroller with 74% free safety headroom remaining.

Pillar 2

Vocabulary & Hallucination Boundary

Regular LLMs can assemble arbitrary toxic, violent, or dangerous strings because subword BPE permits open generation. In contrast, the StoryLM's output projection head contains only 3,509 rows: unapproved words simply have no representation in silicon.

Pillar 3

Head Cost & Memory Bandwidth

In open LLMs, the classification head (e.g. 128k vocab × 4096 dim) accounts for over 60% of inference latency. The StoryLM's tied 3,509-word head requires only 449K operations per token, allowing seamless 250+ tokens/sec execution without starving hardware memory channels.

Pillar 4

Zero-Underrun Audio Coupling

Because StoryLM drafts an entire 23-line bedtime story in under 1 second, generation is ~30× faster than human playback (111 seconds). Sentences are passed to an IMA ADPCM audio DMA stream with guaranteed zero audio glitching or buffer starvation.
